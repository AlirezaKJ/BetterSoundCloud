# BetterSoundCloud v2 — Backlog

This is the working backlog for the v2 rewrite. It supersedes the scattered survey notes: ~229 raw entries were deduplicated into the items below (five separate surveys had independently written up the settings panel, the tray, electron-updater, AudioMonitor and the load-failure surface).

**How to read an item.** Every item carries a source label — `parity: v0.7.x`, `parity: soundcloud-rpc`, `user request`, `infrastructure`, or `proposal` — plus the file/issue/phase it traces to and a rough effort (S / M / L / XL). Nothing is here that does not trace to code, an issue, or the roadmap.

**Ordering.** Milestones run in the order the work should actually happen. Milestone 1 is deliberately not feature work: four of the highest-priority items below were written against an _unverified_ assumption about how SoundCloud's sign-in is reached, and one instrumented run decides whether the headline fix is a total blocker or a no-op. **That run happened on 2026-09-08** — the assumption was wrong in both of its competing forms, and Milestone 3's headline item shrank accordingly. Milestone 1 records what was measured; the one part still open needs a real sign-in attempt.

**Scope.** The project's posture is _parity, not evasion_: make a real desktop client look like the ordinary browser it wraps, for real logged-in users. See "Explicitly declined".

- [x] **Verify how sign-in is actually reached, before writing the popup fix** — ANSWERED 2026-09-08
      Log every URL that reaches `setWindowOpenHandler` and every URL that reaches `will-navigate` on the content view, then click Sign in on a real launch. Two surveys assert opposite mechanisms and neither verified it in this tree: one says sign-in is a `window.open` popup that gets externalised, the other says `secure.soundcloud.com` being in `ALLOWED_HOSTS` means it signs in _in place_ — the second is wrong reasoning (`ALLOWED_HOSTS` gates `will-navigate` only, never `window.open`), but that does not make the first true.

  **Finding: neither. It is an in-page iframe.** On a logged-out profile with both handlers instrumented, clicking Sign in fires **neither** `setWindowOpenHandler` **nor** `will-navigate`, and the top-level URL stays on `/discover`. What appears is a 450×900 iframe inside a modal `div`, at `https://secure.soundcloud.com/web-auth?client_id=…&device_id=…&theme=dark&ui_evo=true`, listed by `mainFrame.framesInSubtree`.

  So sign-in already happens in-app — but **not** because `secure.soundcloud.com` sits in `ALLOWED_HOSTS`. Iframe loads never consult `isInternalUrl` at all; that allowance is doing nothing here. Neither handler governs sign-in, so neither is the fix.

  Re-run with a real injected input event (`sendInputEvent` down+up, which grants transient user activation) to rule out Chromium silently swallowing an unactivated `window.open`: identical result. The popup path is genuinely unused, not suppressed.

  Also settled: the earlier `frame-ancestors 'none'` capture was taken against `/sign-in`. The surface actually embedded is `/web-auth`, which permits framing.
  `source: proposal` · `evidence: src/main/session.ts:79-82 (no origin test) vs :85-90 (has one); measured 2026-09-08 with scratchpad probes signin-probe.cjs and signin-gesture.cjs` · `effort: S`

## Future / aspirational — post-1.0, not parity work

Kept separate so it is never confused with the work above. Nothing here is scheduled.

- **Local audio file library.** #86 asks to import local mp3/m4a for tracks removed from SoundCloud. It is the only place BSC can own the audio graph, and nothing about it touches soundcloud.com — files served through a custom scheme registered with `protocol.handle` (privileged, `stream: true`, `supportFetchAPI: true` so seeking works), tags via `music-metadata` (pure JS, no native module in the signing matrix), index cached in userData. It needs its own view, its own transport, and a **second source of truth for "what is playing"** that presence, scrobbling, the tray and media keys all have to understand — so define the TrackInfo boundary before writing either. **Do not inject a player into SoundCloud's page**; that is the v0.7.x mistake in a new costume. `#86` · `XL`
- **Offline listening mode.** #27, and it decomposes into the downloader (planned), the local playback surface above, and offline detection routing to it. The middle piece is the same view #86 needs, so scope them together or not at all. Must degrade to "nothing downloaded yet" rather than erroring when the downloader breaks. `#27` · `L`
- **Equaliser — spike the DRM blocker first.** #101 asks for EQ. The only route is `createMediaElementSource()` on the page's audio element plus BiquadFilter nodes. **The blocker is EME, not CORS**: for Widevine-encrypted tracks the decrypted audio is never exposed to Web Audio, and the result is _silence, not an error_ — the identical user-visible symptom as the auto-skip bug, on the same catalogue subset, which will be reported as a regression of #89/#91/#95/#105. Worse, `createMediaElementSource` cannot be undone for the element's lifetime, so if SoundCloud reuses one `<audio>` element, attaching once poisons every later DRM track for the session. **Run that falsification test first** — does the element identity change between tracks? A "no" means this cannot ship in this form at all. Implement EQ in the local library where we own the graph, and offer the SoundCloud-side version at most as an opt-in Tier-2 plugin with an explicit "unavailable on protected tracks" state. `#101` · `L`
- **Crossfade and gapless — local library only.** Both need the next track decoded before the current ends, which on SoundCloud means the private api-v2 plus the page's OAuth token, and is flatly impossible for the encrypted portion of the catalogue. Write a short docs entry declining it for SoundCloud with the DRM reason so it stops being re-requested. `M`
- **Read-only "up next" strip.** Reading SoundCloud's queue means scraping the queue panel (Tier 1, allowed, permanently brittle); _writing_ it means synthetic drag-and-drop (Tier 3) or api-v2 with the user's token. So a queue **manager** is not deliverable on SoundCloud content — ship the strip as a plugin so its selector breakage is opt-in, and a real queue manager for the local library. `L`
- **Install a theme or plugin from a file or URL.** The honest, shippable 80% of a marketplace and the thing that should exist before one: a dialog taking a local file or an https URL, showing the author's metadata, the SHA-256 it will pin, and a badge for the declared capability tier, then installing **disabled**, requiring a second explicit click to enable. Answers #94 with no hosting or moderation infrastructure and establishes the consent flow. Do not let it become the jsDelivr pattern. `#94` · `M`
- **Plugin and theme marketplace.** The full version: a curated index with search, screenshots, declared tier and a pinned SHA-256 per artefact. Most likely to make someone switch, most likely to hurt the project, so last. Four risks in order: it is a code-distribution channel run by a solo maintainer; moderation is permanent and unpaid; a popular Tier-3 plugin undoes the parity posture at the ecosystem level for everyone; and a marketplace implies availability and will be reported as broken when it is down. Prerequisites: Phase 4 shipped, `CUSTOM_PLUGINS.md` normative, the tier contract _enforced_ rather than documented, and install-from-URL already proven. `XL`
- **Local listening statistics.** Append each completed play to a newline-delimited JSON file in userData and aggregate in main — deliberately not SQLite, since a native module would enter the signing and notarization matrix for something an append-only text file handles for years. Constraints that make it acceptable in a no-telemetry project: opt-in, never leaves the machine, one export button, one delete button, stated plainly. This is also the constructive answer to the telemetry question. Accuracy is bounded by AudioMonitor's selectors, so record a schema version per row. `M`

## Open decisions — maintainer's call

- **The playback-control mechanism.** Blocks the tray menu, the thumbar, native media controls, seeking from the showcase and the lyrics pane, and anything else reaching the player from outside the page. See the item in Milestone 7; the decision itself is (a) media-keycode `sendInputEvent`, (b) `.play()`/`.pause()` on the media element from the isolated world, or (c) observe-only. Choosing (a) or (b) without writing down the reasoning re-opens the argument Phase 0.5 closed; choosing (c) quietly kills half the requested roadmap.
- **Is third-party OAuth supported in v2 at all?** The maintainer's own advice on #97 is "don't try Google sign-in, use the username/password attempt", and the passkey/verification-code path is reported failing in #97’s comments and Facebook login in #100. Once first-party sign-in works in-app, username/password is a complete path. Decide explicitly, and if the answer is no, say so _where the user hits it_ rather than building a protocol handler.
- **Windows code signing and macOS notarization funding.** Both are money decisions with technical consequences (SmartScreen reputation; whether macOS artifacts are publishable at all).
- ~~**Discord client ID**~~ — **decided 2026-10-27: reuse `1054636117284106270`**, the BetterSoundCloud application v0.7.x used, so its name and uploaded art carry over. Original question: reuse `1054636117284106270` or register new. Reusing keeps existing users' presence assets; a fresh one gives a clean namespace. Decide before the first alpha: changing it after users have the app in their Discord activity history is visible churn.
- ~~**Default Last.fm API key**~~ — **decided 2026-10-27: ship BetterSoundCloud's own**, with the user's own key and secret as a setting for when it gets revoked. Registered the same day; see the Last.fm item in Milestone 9. Original question: ship one (better UX, extractable from the asar, abuse revokes it for everyone) or keep it user-supplied (friction, no shared fate). Shapes the settings section and the safeStorage schema, so decide before building the service.
- **Telemetry** — none at all, or anonymous opt-in error reporting. Weigh it against the evidence problem this rewrite ran into: the auto-skip bug took four issues and fifteen months partly because there was no signal beyond user prose. The dev-only classifier is the shape of what would be useful — a layer verdict, never content. **If the answer stays "none", say so in the README**, because users ask.
- **Discord presence on by default?** `discord.enabled` defaults to `true`, as it always had in the schema and as v0.7.x behaved, so a fresh install tells the user's Discord friends what they are playing without asking. Keeping it on matches what people installed a client with "Discord Rich Presence" on the box for; turning it off, or asking once on first run, is the privacy-first answer. One value in `src/shared/settings-schema.ts` either way.
- **Ad blocker default-off long-term** — confirm it is the permanent answer rather than a Phase 0.5 safety measure, and define the exception list (nothing on the sign-in or bot-check path is ever filtered). Run falsification test D before deciding.
- **shuffle-fix (#23).** The roadmap lists it among bundled defaults; the safety contract excludes it; the roadmap flags its own contradiction. The substantive call is already made — Tier 3, opt-in, warned, not bundled — what is outstanding is editing the roadmap so the two notes agree, otherwise whoever implements Phase 4 seeding follows whichever note they read first. Then either ship shuffle as an opt-in plugin working through queue navigation, or say on #23 that it cannot be built within the contract and close it. Two years open is worse than a clear no.
- **Configurable user agent.** Roadmap Phase 1 lists it as v0.7.x parity; the Tech Stack thesis is one UA, set once, at the lowest layer, and startup hard-fails if it leaks app identity. These cannot both hold. **Recommendation: do not ship a UA text field** — a user-editable UA is exactly the identity-incoherence generator that produced #106. If an escape hatch is wanted, make it a platform-token picker run through `leaksAppIdentity()`. Record the outcome so it is not relitigated.
- **v0.7.x settings migration** — write the importer (Milestone 8 has an implementable approach) or accept the reset and say so in the release notes. 0.8.0's README and CHANGELOG say they do not come across, which is true of the code today; if the importer ships first, change both.
- **Branding, already settled but unrecorded**: the name stays BetterSoundCloud and the shipped identifier is `com.alirezakj.bettersoundcloud`. The roadmap still names `com.akj.bsc`, which matches nothing in the tree — update the note so a future reader does not "fix" the config to match the doc. Changing the appId after release breaks update continuity and macOS keychain grants.

## Explicitly declined

Recorded so they are not re-proposed, and so the reasons are visible to contributors.

- **Region bypass (#19, #26).** Geo-restriction circumvention is out of scope under _parity, not evasion_. Both threads carry a maintainer comment promising to add an abandoned 2016 Chrome extension, so close them with the posture stated in plain language and a link from CONTRIBUTING, not silently.
- **`sec-ch-ua` rewriting, `navigator.userAgent` redefinition, `navigator.webdriver` overrides, fake `window.chrome`, `--disable-blink-features=AutomationControlled`.** Permanently out of scope; Electron exposes no UserAgentMetadata API, so `navigator.userAgentData.brands` cannot follow a spoofed brand and the result is a _fresh_ contradiction on the exact axis it claims to close. This is what PR #103 currently ships on `main`.
- **`sendInputEvent` to manufacture `isTrusted: true`**, and synthetic `.click()` on any SoundCloud control. Tier 3. Implicated in the like/follow blocks (#75, #91).
- **`cookies.json` session import.** Its whole purpose was working around the login block that Phase 0.5 exists to fix, and a documented "paste your live session tokens into a file" flow is a credential-handling pattern worth retiring rather than blessing. Already `.gitignore`'d in v2 and no import path exists.
- **`start.sh` and `install_bettersoundcloud.sh` as source-tree launchers.** Both `git reset --hard` + `git clean -fd` on every launch. Replaced by real packages; the two files stay only as stand-ins that start nothing and say where the packages are (Milestone 2). Credit ULTRA-VAGUE and the original contributors in the release notes rather than letting them disappear silently (done: CHANGELOG.md's 0.8.0 entry thanks them, and demenik and silverhadch for the Nix flake, which 0.8.0 drops).
- **shuffle-fix as a bundled default.** It walks SoundCloud's webpack module cache and drives paginated bulk loads against the user's authenticated session.
- **AI / ML features.** No recommendation engine, no model-backed anything. #37 (similar tracks) is answered by navigating to SoundCloud's own station route, not by building recommendations.
- **The auto-scroll lazy-load button.** 20 `executeJavaScript` round-trips per second forever is the exact pattern the contract exists to forbid; it defaulted off, and SoundCloud's own infinite scroll has largely made it moot.
- **`bsc://` deep links and the go-to-URL prompt.** The deep-link feature never actually existed (the only evidence is a changelog line; there is no protocol code at fb3bfdd), and neither has an open issue asking for it.
- **Google Cast (#76).** Not a posture decline — a capability that is not available. The Cast sender SDK needs the Chrome Media Router component, which Electron does not ship, so `chrome.cast` is absent and SoundCloud's own cast button cannot work inside the app regardless. Implementing it independently would mean handing a receiver the same Widevine-protected HLS manifests, which needs its own licence flow. Verify the `chrome.cast` absence on the current Castlabs build, then reply with the specific reason and close — saying _which_ of the two kinds of no it is matters for how the reply reads.
- **A Playwright E2E suite.** See Milestone 13.
- **Unrequested feature proposals** — command palette, mini-player, sleep timer, settings export/import. Each traces to no issue, no roadmap line and neither predecessor project. The sleep timer argues against itself: without the playback-control decision its deliverable is muting while the queue keeps advancing, which is materially worse than shipping nothing.
