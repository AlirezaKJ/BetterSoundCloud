# BetterSoundCloud v2 — Backlog

This is the working backlog for the v2 rewrite. It supersedes the scattered survey notes: ~229 raw entries were deduplicated into the items below (five separate surveys had independently written up the settings panel, the tray, electron-updater, AudioMonitor and the load-failure surface).

**How to read an item.** Every item carries a source label — `parity: v0.7.x`, `parity: soundcloud-rpc`, `user request`, `infrastructure`, or `proposal` — plus the file/issue/phase it traces to and a rough effort (S / M / L / XL). Nothing is here that does not trace to code, an issue, or the roadmap.

**Ordering.** Milestones run in the order the work should actually happen. Milestone 1 is deliberately not feature work: four of the highest-priority items below are currently written against an _unverified_ assumption about how SoundCloud's sign-in is reached, and one twenty-minute instrumented run decides whether the headline fix is a total blocker or a no-op.

**Scope.** The project's posture is _parity, not evasion_: make a real desktop client look like the ordinary browser it wraps, for real logged-in users. See "Explicitly declined".

## Milestone 1 — Diagnose before building

No feature code in this milestone. Four of the P0 items below are currently written against contradictory assumptions, and one of them (the fingerprint audit) cannot be run at all until the first item answers its question.

- [ ] **Verify how sign-in is actually reached, before writing the popup fix**
      Log every URL that reaches `setWindowOpenHandler` and every URL that reaches `will-navigate` on the content view, then click Sign in on a real launch. Two surveys assert opposite mechanisms and neither verified it in this tree: one says sign-in is a `window.open` popup that gets externalised, the other says `secure.soundcloud.com` being in `ALLOWED_HOSTS` means it signs in _in place_ — the second is wrong reasoning (`ALLOWED_HOSTS` gates `will-navigate` only, never `window.open`), but that does not make the first true.
      `source: proposal` · `evidence: src/main/session.ts:79-82 (no origin test) vs :85-90 (has one); prior capture of frame-ancestors 'none' on secure.soundcloud.com/sign-in was against v0.7.x's <webview>` · `effort: S`

- [ ] **Capture the sign-in failure reason code, not just the fingerprint**
      SoundCloud's auth module returns a named failure reason on a blocked sign-in — `DATADOME_BLOCKED`, `DEVICE_TOKEN_FAILED`, `RECAPTCHA_FAILED`, `DATADOME_CHECK_REQUIRED`. These have different causes and different fixes: a device-token failure points at client identity we control, a DataDome block points at IP/session reputation we do not. Without this the fingerprint audit can come back completely clean while the block persists, and the project has no next move.
      `source: user request` · `evidence: #93, #97, #110, #111; captured sign-in page ships window.__sc_features with datadome/recaptcha killswitches` · `effort: S`

- [ ] **Freeze `src/preload/content.ts` and the shared session until a clean baseline is recorded**
      A written sequencing rule, not code. The empty `start()` and the single shared session are the _control condition_ for the login and like/follow clusters — the only controlled experiment this project will get. AudioMonitor, the adblocker and the session partition each destroy it; they must land one at a time with a login retest between, and the fingerprint audit plus a clean login pass must be recorded against today's build first.
      `source: proposal` · `evidence: src/preload/content.ts:82-90 (deliberately empty); src/main/window.ts:72-73 (hardenSession called twice on the same defaultSession); src/main/diagnostics.ts:14-16 (v0.7.x's confounded-causes failure)` · `effort: S`

- [ ] **Prove the packaged renderer actually executes under its own CSP**
      In production the header and settings views load over `file://` from inside `app.asar`, and the built HTML emits `<script type="module" crossorigin src="…">` under `default-src 'none'; script-src 'self'`. Nobody has ever launched the packaged app: dev loads over `http://localhost:5173` where both trivially pass. The failure is silent by construction — `window.show()` fires on the header's `did-finish-load`, which fires whether or not the module ran, so a blocked script gives an empty 32px strip and a normal-looking window.
      `source: proposal` · `evidence: out/renderer/header/index.html; src/main/window.ts:88, :100, :173-177; .github/workflows/ci.yml:49 ends at npm run pack with no launch` · `effort: S`

- [ ] **Run the fingerprint parity audit in whichever sign-in surface item 1 identifies**
      Dump `navigator.userAgent`, `navigator.userAgentData.getHighEntropyValues`, `navigator.webdriver`, `navigator.plugins.length`, `navigator.languages` and the `sec-ch-ua*` headers _as actually sent_, in three places: real Chrome on the same machine, the v2 content view, and the v2 sign-in surface. Commit the diff. Fold in the falsification tests: `typeof process|global|require` all undefined on the sign-in origin, `Object.getOwnPropertyDescriptor(navigator,'userAgent')` undefined, `navigator.hasOwnProperty('webdriver')` false, and zero `console.log` calls per second with a track playing. **Do not add spoofing if a mismatch appears** — a mismatch means identity is set in the wrong place and the fix is to move it lower.
      `source: user request` · `evidence: roadmap Phase 0.5 (unchecked); src/main/index.ts:20-36; #106, #93, #97` · `effort: M`

## Milestone 3 — Phase 0.5 close-out: the login / blocked cluster

The remaining headline bug. This is the only milestone where "the app is not credible without it" is literally true.

- [ ] **Keep SoundCloud's own sign-in inside the app; route only third-party OAuth out**
      `setWindowOpenHandler` returns `{action:'deny'}` for **every** URL and calls `shell.openExternal`, with no origin test — while the `will-navigate` handler ten lines below it does check. If sign-in is a first-party popup, it opens in the user's real browser, authenticates there, and drops the cookie in the wrong jar: the app stays logged out no matter how many times the user succeeds. That is #110 and #74 verbatim. Branch on `isInternalUrl()`; internal origins get `{action:'allow'}` with `overrideBrowserWindowOptions` carrying the same preload, the same `userAgent`, `contextIsolation`, `sandbox`, and — critically — **the same session object taken by reference**, never a fresh partition or `defaultSession`. Add a `will-navigate` allowance so the popup can redirect within `secure.soundcloud.com`. Effort is L, not M: verification means confirming the cookie lands in the content view's jar, not that a window opened. **Blocked on Milestone 1 item 1** — if sign-in navigates in place, this shrinks to nothing.
      `source: user request` · `evidence: src/main/session.ts:78-90; src/main/session.test.ts covers isInternalUrl but never the window-open path; #110, #74, #58, #111, #100` · `effort: L`

- [ ] **Give the content view a visible, recoverable failure state**
      `did-fail-load` exists and correctly filters `ERR_ABORTED` and subframes, but its only action is `console.error` — invisible in a packaged build, so the user's experience is unchanged from #50. On a main-frame failure, load a bundled local error page into the content view with the error code, a Retry, and an Open Settings button, plus `net` online/offline driving a backoff retry. Make it a **real navigation, not an overlay** — v0.7.x's `#loadingscreen` was an overlay dismissed by the last statement of an unguarded block, which is what stranded #109 and #55. Add `render-process-gone` and `unresponsive` while here. Gotcha: **do not try to detect blocks here** — a DataDome interstitial returns HTTP 200 and never reaches `did-fail-load`.
      `source: user request` · `evidence: src/main/window.ts:145-148; #109, #55, #50, #96, #38, #48` · `effort: M`

- [ ] **Add a `did-fail-load` and timeout safety net on the _header_ view**
      `header.webContents.once('did-finish-load', () => window.show())` is the **only** call to `window.show()` in the codebase. Any failure to load our own chrome — a wrong `file://` path, an asar-integrity mismatch, a renderer crash before first paint, a CSP problem — produces a process that runs forever, holds the single-instance lock, shows nothing, and can only be killed from Task Manager. Gating on the header rather than the content view is correct and should stay; it just needs a `did-fail-load`, a `render-process-gone`, and a 2-3s hard timeout that shows the window regardless.
      `source: proposal` · `evidence: src/main/window.ts:100 (sole show() call), :145-148 (did-fail-load on content only)` · `effort: S`

- [ ] **Show a window before the Widevine CDM bootstrap finishes**
      `createShell` runs only after `components.whenReady()` resolves. On first run that downloads and registers the CDM, and until it resolves there is no window at all — the user double-clicks, nothing happens, they double-click again and the single-instance lock makes it a silent no-op. If the fetch fails (offline first run, corporate proxy, AppImage read-only mount) the chain lands in `console.error` + `app.quit()`: an instant exit with no message, which is indistinguishable from #96. Create and show the shell _before_ the gate with a chrome-owned "starting up" state, gate only the content view's first navigation, put a hard timeout on `whenReady()`, and on rejection show a real message. Gotcha: move the _window_, never the gate — the CDM must still be registered before any EME call.
      `source: user request` · `evidence: src/main/index.ts:51, :60-67, :75-78; src/main/window.ts:41, :100; #96, #50, #55` · `effort: M`

- [ ] **Neuter `general.minimizeToTray` until a tray exists**
      `index.ts:107` calls `shell.window.hide()` when the setting is on, and there is no `Tray` anywhere in `src/`. `window-all-closed` never fires (hidden is not closed) and `second-instance` calls `restore()`/`focus()` but never `show()`, so relaunching cannot bring it back — only Task Manager can. The strand is currently _unreachable_ because the setting defaults false and the settings panel does not load, which is exactly why this must land before the panel does. One line: gate the hide on a tray existing, or delete the branch.
      `source: parity: v0.7.x` · `evidence: src/main/index.ts:105-109; src/shared/settings-schema.ts:55-60; grep Tray src/ returns only schema hits; #54` · `effort: S`

- [ ] **Mark the eight inert settings in the schema before the panel becomes reachable**
      Only three of eleven schema keys have a reader anywhere in `src/`: `minimizeToTray`, `zoomFactor`, `hardwareAcceleration`. The other eight do nothing, and two of them _state behaviour that does not exist_ — `shortcuts.mediaKeys` help says "Handled by SoundCloud's own Media Session handlers" and `general.checkForUpdates` help promises auto-disable on distro packages. The moment the panel ships, that is a guaranteed wave of "this toggle does nothing" reports on the release meant to restore trust. Add one optional `wired?: false` field on `Base`, rendered as a disabled control with a note, cleared per key as each feature lands. Hard precondition on the settings-panel item, not a follow-up.
      `source: proposal` · `evidence: src/shared/settings-schema.ts:47-133; readers only at src/main/index.ts:47, :107, :139; help text at :66 and :112-114` · `effort: S`

- [ ] **Give the content view its own session partition — and ship the cookie migration with it**
      Both views currently resolve to `session.defaultSession`, so `hardenSession` runs twice on the same object and the second call silently replaces the first's permission handlers (the `mediaKeySystem` allowlist that DRM depends on survives only because the two calls are identical). A partition is required before the adblocker can be "scoped to the SoundCloud session only". **The consequence nobody wrote down: cookies live in the session, so switching partitions signs every existing user out** — in an app whose most-reported problem is that signing back in gets you blocked, and on Windows it specifically destroys the working v0.7.x login that the userData item preserves. Land it before the first public artifact, or ship a one-time copy of soundcloud.com cookies and localStorage into the new partition. Verify Widevine in the non-default partition **before** shipping: a CDM failure there presents as greyed-out auto-skipping tracks, i.e. indistinguishable from the bug just fixed.
      `source: proposal` · `evidence: src/main/window.ts:46-75, :72-73; src/main/diagnostics.ts:45-48; src/main/session.ts:44-53; Tech Stack §5 adblocker bullet` · `effort: L`

- [ ] **Document the profile-reset path, per OS, in the README and the issue template**
      A user on #97 discovered that deleting `%AppData%\BetterSoundCloud` and reinstalling clears the "you have been blocked" interstitial. That is the highest-value self-service step in the entire tracker and it appears nowhere in the app, the README or the docs. State what deleting it costs (signs you out, loses settings and window state), and state that uninstalling does **not** do it — `nsis.deleteAppDataOnUninstall` is unset, which is why the reporter had to do it by hand after a reinstall changed nothing.
      `source: user request` · `evidence: #97; electron-builder.yml:55-60; README.md (no profile paths)` · `effort: S`

- [ ] **Add a safe-mode launch flag that disables hardware acceleration without the UI**
      `advanced.hardwareAcceleration` is read pre-ready and gates `app.disableHardwareAcceleration()`. Turning it off is the standard fix for the blank/black-window class of failure — and the only way to change it is a settings panel that needs a visible window, i.e. the thing the GPU has broken. Read an env var or a `--safe-mode` argv flag in the same pre-ready block, have it also skip the adblocker and plugin loading once those exist, and document it. This becomes the standard triage reply for every blank-window report, replacing the current one ("try a VPN") which addresses a different cause entirely.
      `source: proposal` · `evidence: src/main/index.ts:47-49; src/shared/settings-schema.ts:127-133; #50, #55, #109` · `effort: S`

Nothing publishes today. The updater, the signing decisions and the Linux verification all sit behind this.

## Future / aspirational — post-1.0, not parity work

Kept separate so it is never confused with the work above. Nothing here is scheduled.

- **Local audio file library.** #86 asks to import local mp3/m4a for tracks removed from SoundCloud. It is the only place BSC can own the audio graph, and nothing about it touches soundcloud.com — files served through a custom scheme registered with `protocol.handle` (privileged, `stream: true`, `supportFetchAPI: true` so seeking works), tags via `music-metadata` (pure JS, no native module in the signing matrix), index cached in userData. It needs its own view, its own transport, and a **second source of truth for "what is playing"** that presence, scrobbling, the tray and media keys all have to understand — so define the TrackInfo boundary before writing either. **Do not inject a player into SoundCloud's page**; that is the v0.7.x mistake in a new costume. `#86` · `XL`
- **Offline listening mode.** #27, and it decomposes into the downloader (planned), the local playback surface above, and offline detection routing to it. The middle piece is the same view #86 needs, so scope them together or not at all. Must degrade to "nothing downloaded yet" rather than erroring when the downloader breaks. `#27` · `L`
- **Equaliser — spike the DRM blocker first.** #101 asks for EQ. The only route is `createMediaElementSource()` on the page's audio element plus BiquadFilter nodes. **The blocker is EME, not CORS**: for Widevine-encrypted tracks the decrypted audio is never exposed to Web Audio, and the result is _silence, not an error_ — the identical user-visible symptom as the auto-skip bug, on the same catalogue subset, which will be reported as a regression of #89/#91/#95/#105. Worse, `createMediaElementSource` cannot be undone for the element's lifetime, so if SoundCloud reuses one `<audio>` element, attaching once poisons every later DRM track for the session. **Run that falsification test first** — does the element identity change between tracks? A "no" means this cannot ship in this form at all. Implement EQ in the local library where we own the graph, and offer the SoundCloud-side version at most as an opt-in Tier-2 plugin with an explicit "unavailable on protected tracks" state. `#101` · `L`
- **Crossfade and gapless — local library only.** Both need the next track decoded before the current ends, which on SoundCloud means the private api-v2 plus the page's OAuth token, and is flatly impossible for the encrypted portion of the catalogue. Write a short docs entry declining it for SoundCloud with the DRM reason so it stops being re-requested. `M`
- **Read-only "up next" strip.** Reading SoundCloud's queue means scraping the queue panel (Tier 1, allowed, permanently brittle); _writing_ it means synthetic drag-and-drop (Tier 3) or api-v2 with the user's token. So a queue **manager** is not deliverable on SoundCloud content — ship the strip as a plugin so its selector breakage is opt-in, and a real queue manager for the local library. `L`
- **Install a theme or plugin from a file or URL.** The honest, shippable 80% of a marketplace and the thing that should exist before one: a dialog taking a local file or an https URL, showing the author's metadata, the SHA-256 it will pin, and a badge for the declared capability tier, then installing **disabled**, requiring a second explicit click to enable. Answers #94 with no hosting or moderation infrastructure and establishes the consent flow. Do not let it become the jsDelivr pattern. `#94` · `M`
- **Plugin and theme marketplace.** The full version: a curated index with search, screenshots, declared tier and a pinned SHA-256 per artefact. Most likely to make someone switch, most likely to hurt the project, so last. Four risks in order: it is a code-distribution channel run by a solo maintainer; moderation is permanent and unpaid; a popular Tier-3 plugin undoes the parity posture at the ecosystem level for everyone; and a marketplace implies availability and will be reported as broken when it is down. Prerequisites: Phase 4 shipped, `CUSTOM_PLUGINS.md` normative, the tier contract _enforced_ rather than documented, and install-from-URL already proven. `XL`
- **Local listening statistics.** Append each completed play to a newline-delimited JSON file in userData and aggregate in main — deliberately not SQLite, since a native module would enter the signing and notarization matrix for something an append-only text file handles for years. Constraints that make it acceptable in a no-telemetry project: opt-in, never leaves the machine, one export button, one delete button, stated plainly. This is also the constructive answer to the telemetry question. Accuracy is bounded by AudioMonitor's selectors, so record a schema version per row. `M`

## Open decisions — maintainer's call

- **The playback-control mechanism.** Blocks the tray menu, the thumbar, native media controls, and anything else reaching the player from outside the page. See the item in Milestone 7; the decision itself is (a) media-keycode `sendInputEvent`, (b) `.play()`/`.pause()` on the media element from the isolated world, or (c) observe-only. Choosing (a) or (b) without writing down the reasoning re-opens the argument Phase 0.5 closed; choosing (c) quietly kills half the requested roadmap.
- **Is third-party OAuth supported in v2 at all?** The maintainer's own advice on #97 is "don't try Google sign-in, use the username/password attempt", and the passkey/verification-code path is reported failing in #97’s comments and Facebook login in #100. Once first-party sign-in works in-app, username/password is a complete path. Decide explicitly, and if the answer is no, say so _where the user hits it_ rather than building a protocol handler.
- **Windows code signing and macOS notarization funding.** Both are money decisions with technical consequences (SmartScreen reputation; whether macOS artifacts are publishable at all).
- **Discord client ID** — reuse `1054636117284106270` or register new. Reusing keeps existing users' presence assets; a fresh one gives a clean namespace. Decide before the first alpha: changing it after users have the app in their Discord activity history is visible churn.
- **Default Last.fm API key** — ship one (better UX, extractable from the asar, abuse revokes it for everyone) or keep it user-supplied (friction, no shared fate). Shapes the settings section and the safeStorage schema, so decide before building the service.
- **Telemetry** — none at all, or anonymous opt-in error reporting. Weigh it against the evidence problem this rewrite ran into: the auto-skip bug took four issues and fifteen months partly because there was no signal beyond user prose. The dev-only classifier is the shape of what would be useful — a layer verdict, never content. **If the answer stays "none", say so in the README**, because users ask.
- **Ad blocker default-off long-term** — confirm it is the permanent answer rather than a Phase 0.5 safety measure, and define the exception list (nothing on the sign-in or bot-check path is ever filtered). Run falsification test D before deciding.
- **shuffle-fix (#23).** The roadmap lists it among bundled defaults; the safety contract excludes it; the roadmap flags its own contradiction. The substantive call is already made — Tier 3, opt-in, warned, not bundled — what is outstanding is editing the roadmap so the two notes agree, otherwise whoever implements Phase 4 seeding follows whichever note they read first. Then either ship shuffle as an opt-in plugin working through queue navigation, or say on #23 that it cannot be built within the contract and close it. Two years open is worse than a clear no.
- **Configurable user agent.** Roadmap Phase 1 lists it as v0.7.x parity; the Tech Stack thesis is one UA, set once, at the lowest layer, and startup hard-fails if it leaks app identity. These cannot both hold. **Recommendation: do not ship a UA text field** — a user-editable UA is exactly the identity-incoherence generator that produced #106. If an escape hatch is wanted, make it a platform-token picker run through `leaksAppIdentity()`. Record the outcome so it is not relitigated.
- **v0.7.x settings migration** — write the importer (Milestone 8 has an implementable approach) or accept the reset and say so in the release notes.
- **Branding, already settled but unrecorded**: the name stays BetterSoundCloud and the shipped identifier is `com.alirezakj.bettersoundcloud`. The roadmap still names `com.akj.bsc`, which matches nothing in the tree — update the note so a future reader does not "fix" the config to match the doc. Changing the appId after release breaks update continuity and macOS keychain grants.

## Explicitly declined

Recorded so they are not re-proposed, and so the reasons are visible to contributors.

- **Region bypass (#19, #26).** Geo-restriction circumvention is out of scope under _parity, not evasion_. Both threads carry a maintainer comment promising to add an abandoned 2016 Chrome extension, so close them with the posture stated in plain language and a link from CONTRIBUTING, not silently.
- **`sec-ch-ua` rewriting, `navigator.userAgent` redefinition, `navigator.webdriver` overrides, fake `window.chrome`, `--disable-blink-features=AutomationControlled`.** Permanently out of scope; Electron exposes no UserAgentMetadata API, so `navigator.userAgentData.brands` cannot follow a spoofed brand and the result is a _fresh_ contradiction on the exact axis it claims to close. This is what PR #103 currently ships on `main`.
- **`sendInputEvent` to manufacture `isTrusted: true`**, and synthetic `.click()` on any SoundCloud control. Tier 3. Implicated in the like/follow blocks (#75, #91).
- **`cookies.json` session import.** Its whole purpose was working around the login block that Phase 0.5 exists to fix, and a documented "paste your live session tokens into a file" flow is a credential-handling pattern worth retiring rather than blessing. Already `.gitignore`'d in v2 and no import path exists.
- **`start.sh` and `install_bettersoundcloud.sh` as source-tree launchers.** Both `git reset --hard` + `git clean -fd` on every launch. Replaced by real packages. Credit ULTRA-VAGUE and the original contributors in the release notes rather than letting them disappear silently.
- **shuffle-fix as a bundled default.** It walks SoundCloud's webpack module cache and drives paginated bulk loads against the user's authenticated session.
- **AI / ML features.** No recommendation engine, no model-backed anything. #37 (similar tracks) is answered by navigating to SoundCloud's own station route, not by building recommendations.
- **The auto-scroll lazy-load button.** 20 `executeJavaScript` round-trips per second forever is the exact pattern the contract exists to forbid; it defaulted off, and SoundCloud's own infinite scroll has largely made it moot.
- **`bsc://` deep links and the go-to-URL prompt.** The deep-link feature never actually existed (the only evidence is a changelog line; there is no protocol code at fb3bfdd), and neither has an open issue asking for it.
- **Google Cast (#76).** Not a posture decline — a capability that is not available. The Cast sender SDK needs the Chrome Media Router component, which Electron does not ship, so `chrome.cast` is absent and SoundCloud's own cast button cannot work inside the app regardless. Implementing it independently would mean handing a receiver the same Widevine-protected HLS manifests, which needs its own licence flow. Verify the `chrome.cast` absence on the current Castlabs build, then reply with the specific reason and close — saying _which_ of the two kinds of no it is matters for how the reply reads.
- **A Playwright E2E suite.** See Milestone 13.
- **Unrequested feature proposals** — command palette, mini-player, sleep timer, settings export/import. Each traces to no issue, no roadmap line and neither predecessor project. The sleep timer argues against itself: without the playback-control decision its deliverable is muting while the queue keeps advancing, which is materially worse than shipping nothing.
